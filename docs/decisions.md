- 2026-10-05: Dropped `Error::NotYetExpired` from the escrow contract's error enum (spec originally listed it in section 8). Reason: Soroban's `require_auth()` auth model has no path for a contract to return a graceful `Result::Err` when a non-admin calls `refund()` before the deadline; `require_auth()` either succeeds or the host aborts the transaction with its own authorization error, which is not a contract `Error` variant. `refund()` still enforces "anyone after deadline, admin anytime" correctly (verified by test); the variant was unreachable under any correct implementation, so it was removed rather than left dead. David confirmed via AskUserQuestion. Error discriminants renumbered 1-7 (contract not yet deployed, so no on-chain compatibility concern). technical-doc.md section 8 updated to match.
- 2026-10-05: `Error::NotAssigned` in `release()` was also dead code (the `task.worker.ok_or(NotAssigned)` check can never fire, since `assign()` is the only path to `TaskStatus::Assigned` and it always sets `worker` in the same write). Simplified to `task.worker.clone().unwrap()` with a comment explaining the invariant. Kept the `Error::NotAssigned` variant defined (spec section 8 lists it, and a future `transition()` change in Phase 2 might introduce a real path that needs it) rather than removing it, since it costs nothing to leave unused and removing+re-adding later is more churn than leaving it. David confirmed via AskUserQuestion.

Reason: `@stellar/stellar-sdk/contract`'s `Client` always derives `errorTypes` from the deployed contract's own `spec.errorCases()`, which reads each variant's Rust doc comment as the message `unwrapErr()` returns; with no doc comments every message was empty. Verified live against the redeployed contract. - 2026-10-05: Verified `db.transaction()` (needed for `transition()`'s atomic status-update-plus-task_events-write, SPEC.md section 4) is safe to use against the remote, HTTP-based `libsql://` Turso connection, not just a local `file:` database. An initial web search suggested Turso's HTTP API is "stateless" with interactive BEGIN/COMMIT/ROLLBACK "off-limits," which would have been a serious correctness problem for the whole state machine. Did not take that at face value: read the actual installed `@libsql/client@0.18.0` source directly. Its HTTP client's `transaction()` returns a genuine `HttpTransaction` built on `openStream()` (a persistent Hrana protocol stream/session, not independent one-shot requests), and `drizzle-orm/libsql`'s own `transaction()` calls straight through to it. The web search's claim describes an older or more limited API surface than what ships today; verified against real installed source, not assumed either way.
